# 安全审计暂不修复项说明

## 1. 文档目的

本文记录 2026-08-20 安全审计后明确决定暂不修改的风险项，避免后续维护时将其误判为
遗漏、重复修复，或在不了解上下游兼容约束的情况下直接改动协议。

这里的“暂不修复”表示当前版本接受风险，并不表示问题不存在或没有更安全的方案。
任何一项的部署前提不再成立时，都必须重新评估。

## 2. 决策总览

| 风险项 | 当前决定 | 主要原因 |
| --- | --- | --- |
| XFF/客户端 IP 信任模型 | 暂不修改应用代码 | 改动会同时影响 CDN、反向代理、IP 白名单、登录风控和审计日志，需要先确定可信代理拓扑 |
| 资源 API Key 的完整授权能力 | 保留现有能力 | 它是现有上下游财务系统的服务凭据，单边缩权会破坏已有接口调用 |
| 上下游认证与传输协议 | 不做单边协议重构 | 双向 TLS、IP 白名单、请求签名和权限范围需要上下游共同部署，单边改协议无法兼容旧节点 |

## 3. XFF 与客户端 IP

### 3.1 保留的现状

`get_client_ip6()` 及框架客户端 IP 获取逻辑仍可能采用 `X-Forwarded-For` 或
`HTTP_CLIENT_IP`。本轮不修改其取值顺序，也不统一改成 `REMOTE_ADDR`。

相关实现和使用点包括：

- `app/common.php` 中的 `get_client_ip6()`；
- `ApiCheck` 的 IP 白名单；
- 登录频率限制、登录记录和 API 日志；
- 需要向上游传递客户端地址的兼容流程。

### 3.2 不直接修改的原因

系统可能部署在 CDN、WAF 或 Nginx 反向代理之后。直接忽略 XFF 会把所有客户识别为代理
节点地址，导致白名单、限流、审计和区域判断发生行为变化；继续无条件信任 XFF 则允许
客户端伪造地址。正确处理依赖生产环境的实际代理链，无法仅凭仓库代码确定。

### 3.3 当前缓解要求

- 公网入口必须由唯一受控的 CDN、WAF 或反向代理接收请求；后端源站不得直接暴露。
- 在反向代理层覆盖客户端传入的转发头，不得把原始 XFF 原样透传。
- 只信任固定代理出口地址，并在防火墙限制源站访问来源。
- IP 白名单不得作为资源 API 的唯一认证条件。
- 重要操作日志同时保留代理连接地址和规范化后的客户地址。

### 3.4 重新评估条件

确定生产代理拓扑、可信代理 IP 段及 CDN 回源规则后，应改为“只信任已知代理设置的真实
IP 头”；如果源站需要允许直连，则直连请求只能使用 `REMOTE_ADDR`。

## 4. 资源 API Key 的完整授权能力

### 4.1 保留的现状

资源 API Key 继续用于 `/zjmf_api_login`，成功后签发带 `is_api=1` 的 JWT，并调用现有
上下游业务接口。API Key 仍是一个高权限服务凭据，不在本轮拆分为只读、下单、产品操作
等细粒度权限。

API Key 的查看、重置和启停仍按现有客户后台协议工作。本轮不单独修改上下游登录请求和
响应字段。

### 4.2 不直接修改的原因

当前上下游协议没有 `scope`、客户端身份、密钥版本或能力协商。仅在本分支缩小 JWT 权限
会使旧下游调用失败；仅改变密钥格式或登录字段也会造成不同版本财务系统无法互联。
这类变更必须由上下游同时升级，并保留明确的版本协商或兼容周期。

### 4.3 当前缓解要求

- API Key 按管理员凭据级别保管，不得写入工单、浏览器日志、错误日志或公开配置。
- 上下游站点必须使用 HTTPS，禁止通过公网明文 HTTP 对接。
- 不使用时关闭客户的资源 API；下游停止合作后立即重置 API Key。
- 为每个下游使用独立客户账号和独立 API Key，禁止多个下游共享同一凭据。
- 监控 API 登录、异常调用量和来源变化，并保留密钥轮换记录。

### 4.4 重新评估条件

出现不受完全信任的下游、需要第三方开放接入、单个密钥服务多个系统，或发生密钥泄露
事件时，必须升级为版本化凭据和权限范围模型，至少提供独立客户端、scope、吊销、轮换、
最后使用时间和审计能力。

## 5. 上下游认证与传输协议

### 5.1 保留的现状

本轮不把历史上下游接口整体改造成双向 TLS，也不单边增加强制 IP 白名单、请求签名、
nonce 或新的认证字段。现有上游登录和 JWT 调用契约保持兼容。

`app/zjmf.php` 的历史 cURL 封装目前还关闭了 `CURLOPT_SSL_VERIFYPEER` 和
`CURLOPT_SSL_VERIFYHOST`。因此即使地址使用 HTTPS，客户端也没有严格验证对端身份，
中间人风险仍然存在；本轮记录该风险，但不做单边切换。

这不包括已确认可在本地完成且不会改变协议的授权修复。例如：按当前用户校验资源归属、
精确匹配下游 Token、禁用不需要的售后登录入口，仍应在本地修复。

### 5.2 不直接修改的原因

双向 TLS、证书固定、IP 白名单和新版请求签名都要求通信两端共同配置。只修改一端会直接
中断商品同步、库存同步、下单、开通、续费、工单传递等链路。当前也没有协议版本协商，
无法让新旧认证方式自动共存。

这不是“被劫持也无法修复”。更准确的结论是：可以通过双向 TLS、受信 IP、请求签名和
短期凭据降低风险，但需要作为一次上下游联合升级实施，不能作为本分支的单边补丁发布。

### 5.3 当前缓解要求

- 所有上下游地址使用有效 HTTPS 证书，禁止为了接入而降级到 HTTP。由于当前客户端未
  严格校验证书，这只能避免明文传输，不能单独证明对端身份。
- 在双方条件允许时，先在防火墙或反向代理增加固定来源 IP 白名单。
- 源站仅开放必要接口和端口，不对上下游凭据提供额外的浏览器或日志暴露面。
- 上游地址、API Key、JWT 和下游 Token 不得进入用户可见错误信息。
- 对下单、开通和续费保留幂等键及审计记录，以便识别重放或异常调用。

### 5.4 重新评估条件

新增第三方下游、上下游跨越不可信网络、发生 DNS/TLS/代理劫持事件，或双方均能安排版本
升级时，应启动新版协议。推荐至少包含：严格服务端 TLS 校验、可选双向 TLS、客户端级
凭据、带时间戳和 nonce 的完整请求签名、权限范围、密钥轮换和协议版本协商。

## 6. 不属于暂不修复项的内容

以下问题不能引用本文作为不修复依据：

- 接口接受请求参数中的 `uid` 导致越权；
- 下游 Token 回查未校验客户归属或使用模糊匹配；
- `/resource_login_supplier` 售后登录入口；
- 短信或邮件验证码缺少跨入口、按接收目标和全站维度的限流；
- 零元购、越权续费和其他服务端价格或资源归属校验问题。

这些问题可以在不改变上下游协议的前提下本地修复，不属于兼容性接受风险。

“上游名称或内部诊断信息是否应向客户展示”目前没有形成接受风险决议，仍需按具体字段
和业务用途复核，也不得因为本文而默认保留。

## 7. 维护要求

- 每次安全审计或上下游协议升级后复核本文。
- 新增暂不修复项必须写明负责人、部署前提、缓解措施和重新评估条件。
- 已完成修复的项目应从本文移除，并在提交说明或回归测试中记录。
- 不得用“兼容性”笼统拒绝本地可完成的鉴权、归属、输入校验和限流修复。
